# Pipeline Explanation — Developer–LLM Interaction Mining & Prediction

**Project:** GitHub Repo Miner / SpecStory Prompt Research Pipeline  
**Author context:** Research documentation for advisors and reproducibility  
**Canonical dataset:** `outputs/datasets/specstory_prompts_clustered.csv` (3,673 prompts, 65 repositories)  
**Last verified against codebase:** July 2026

---

# 1. Project Overview

## 1.1 What this project accomplishes

This project builds an end-to-end research pipeline that:

1. **Discovers** public GitHub repositories containing SpecStory session logs (real Cursor/agent chat transcripts).
2. **Extracts** developer user prompts and paired agent responses from those logs.
3. **Cleans and enriches** the data into a structured tabular dataset.
4. **Learns representations** of developer prompts (embeddings, TF-IDF, metadata).
5. **Trains supervised models** to predict what the coding agent will do next — specifically whether it will **generate code** or **use tools**, and (exploratorily) interaction complexity.

The project has evolved from a **descriptive prompt-mining study** (clustering, taxonomy) into an **AI/ML research project** centered on **representation learning and behavior prediction** under weak supervision.

## 1.2 Research motivation

Large language models are now embedded in software development workflows (Cursor, Copilot, Claude Code, etc.), but there is limited **public, reproducible empirical data** about:

- How developers actually write prompts in real repositories
- Whether prompt text contains predictive signal about agent behavior
- Which representations (lexical vs semantic embeddings) best capture developer intent and outcomes

This pipeline addresses that gap by mining **SpecStory** artifacts — markdown files developers optionally commit that record full agent conversations.

## 1.3 Why SpecStory files are useful

SpecStory (`.specstory/history/*.md`) records:

- **User turns** (developer prompts)
- **Assistant turns** (agent responses)
- **Tool-use blocks** (`<tool-use>...</tool-use>`)
- **Fenced code blocks** in agent replies
- **Model names** in speaker headers (when present)

Unlike synthetic benchmarks, SpecStory logs are **in situ**: they reflect real tasks, real repos, and real agent behavior — including noise (CI logs pasted as prompts, short acknowledgments, multilingual text).

Example raw SpecStory structure (from `archive/debug/_trace_source.md`):

```markdown
<!-- Generated by SpecStory -->

# Review TypeScript PluginSystem.ts (2025-04-30 09:43:24)

_**User**_

src\renderer\src\services\PluginSystem.ts  你看看这个

---

_**Assistant**_

---

Read file: src\renderer\src\services\PluginSystem.ts

---

让我继续读这个文件以获取完整的内容。
```

The parser identifies `_**User**_` / `_**Assistant**_` markers (and variants) and pairs each user turn with the following assistant turn.

## 1.4 Problem the pipeline solves

| Problem | Pipeline response |
|---------|-------------------|
| No public corpus of real dev–LLM chats | GitHub mining + SpecStory parsing |
| Messy, noisy transcripts | Rule-based cleaning (`data_cleaning.py`) |
| Unstructured text | CSV with prompts, outcomes, metadata |
| Unknown predictability of agent actions | Supervised ML with repo-held-out evaluation |
| Unclear value of embeddings vs keywords | Representation comparison (SBERT vs TF-IDF) |

## 1.5 Main research question

> **Can we predict what an LLM coding agent will do next based on the current interaction context?**

Operationalized in this repository as three supervised tasks:

| Task | Prediction target | Framing |
|------|-------------------|---------|
| **Task 1** | `primary_intent` (weak label) | Prompt intent classification |
| **Task 2** | `has_generated_code`, `has_tool_use` | **Agent next-action prediction** (core) |
| **Task 3** | response length, code length, session turns | Interaction complexity regression |

Task 2 is the closest direct implementation of the main research question.

## 1.6 Why this matters in the real world

| Domain | Application |
|--------|-------------|
| **Autonomous coding agents** | Route prompts to code vs explanation modes before execution |
| **Efficiency** | Anticipate tool-heavy turns; pre-fetch context |
| **Reliability** | Flag prompts likely to produce large code dumps |
| **Developer tools** | UI hints: "this prompt style usually leads to code generation" |
| **AI safety / monitoring** | Detect unexpected tool-use trajectories |
| **SE research** | Benchmark design grounded in real prompt distributions |

## 1.7 Connection to AI agents and software engineering

- **AI agents:** The pipeline treats the agent as a system whose **observable actions** (code, tools) are prediction targets — a lightweight form of **agent behavior modeling** without training a generative model.
- **Software engineering:** Prompts are studied as artifacts of development practice, similar to commit messages or issue text, but capturing **human–AI collaboration** in real time.

# 4. SpecStory Data Collection

## 4.1 Repository discovery

**Method:** GitHub REST API search (not World of Code directly).

**Entry:** `pipeline.run_pipeline()` in `src/github_repo_miner/pipeline.py`

**Queries** (`src/github_repo_miner/queries.py`):

```python
SPECSTORY_REPO_QUERIES = [
    ("specstory_readme", "specstory in:readme"),
    ("topic_specstory", "topic:specstory"),
    ("specstory_path", "path:.specstory"),
]

SPECSTORY_CODE_QUERIES = [
    ("specstory_history", "path:.specstory/history"),
    ("specstory_root", "path:.specstory"),
    ("specstory_md", "extension:md path:.specstory"),
]
```

**Selection criteria:**

- Public repositories mentioning or containing SpecStory paths
- Code search requires `GITHUB_TOKEN` or `GH_TOKEN` (strongly recommended)
- Default **relaxed filters** (no minimum stars) to maximize coverage
- Optional `--strict-filters` applies stars ≥ 5, age ≥ 3 months, size ≥ 50 KB

**Deduplication** (`pipeline._deduplicate_and_score`):

- One row per `full_name` (repository)
- Aggregates detection signals across queries
- Sorts by `signal_count`, then `stars`

**Outputs:**

| File | Content |
|------|---------|
| `specstory_candidates_<timestamp>.csv` | Filtered candidate repos (480 repos in latest run) |
| `specstory_candidates_raw_<timestamp>.csv` | All deduplicated hits before filtering |

### Function: `search_repos` / `search_code`

**Location:** `src/github_repo_miner/github_api.py`

| | |
|--|--|
| **Input** | Search query string, `max_results` (capped at 1000) |
| **Output** | List of repo metadata dicts, total GitHub count |
| **Logic** | Paginated search with rate-limit backoff; maps API fields to `full_name`, `stars`, `language`, etc. |

## 4.2 SpecStory files

**Path pattern:** `.specstory/history/*.md` (also `.specstory/*.md`)

**Contents:**

- Session title and timestamp
- Alternating User / Assistant turns in markdown
- Tool invocations as XML-like blocks
- Code blocks in agent replies
- Sometimes IDE diagnostics, CI logs, or slash commands (noise)

**Discovery per repo:** `discover_specstory_files(full_name)` walks the GitHub Contents API and optionally falls back to per-repo code search.

## 4.3 Authentication

```python
# config.py
GITHUB_TOKEN = os.getenv("GITHUB_TOKEN") or os.getenv("GH_TOKEN")
```

Without a token: repo search works; code search is skipped; rate limits are stricter.

# 5. Data Extraction Pipeline

## 5.1 Parsing architecture

**Canonical parser:** `specstory_parser.parse_specstory_turns(text)` → `list[SpecStoryTurnPair]`

Each `SpecStoryTurnPair` contains:

```python
@dataclass
class SpecStoryTurnPair:
    prompt_text: str
    agent_response: str = ""
    agent_model: str = ""
    generated_code: str = ""
    code_block_count: int = 0
    code_languages: str = ""
    has_generated_code: bool = False
    has_tool_use: bool = False
```

**Logic:**

1. Scan line-by-line for speaker markers (`User`, `Assistant`, `Human`, `Agent`, etc.)
2. Accumulate lines into turn bodies
3. For each **user** turn, pair with the **next assistant** turn
4. Extract fenced code blocks from assistant text via regex
5. Set `has_generated_code = (code_block_count > 0)`
6. Set `has_tool_use` if `<tool-use>` appears in assistant turn
7. Deduplicate identical `prompt_text` within a file

### Function: `_extract_code_blocks`

```python
_CODE_FENCE_RE = re.compile(r"```(\w+)?[^\n]*\n(.*?)```", re.DOTALL)
```

Returns list of code bodies and language tags.

## 5.2 Extraction paths (two variants)

### Path A — Colab notebook (canonical for ML dataset)

`notebooks/specstory_prompt_miner_colab.ipynb` uses `parse_specstory_turns()` and writes **full turn pairs** including agent response, code flags, `turn_index`.

This path produced the enriched data that, after cleaning and analysis, became `specstory_prompts_clustered.csv`.

### Path B — CLI `extract_specstory_prompts_from_candidates`

**Location:** `prompt_extraction.py`

Currently calls `parse_specstory_prompts()` (prompt strings only) and writes:

```python
{
    "full_name": ...,
    "source_file": ...,
    "prompt_index": ...,
    "prompt_text": ...,
    "prompt_length": ...,
    "artifact_type": "session_prompt",
    "extraction_method": "specstory_turn_parser",
}
```

**Does not include** `agent_response`, `has_generated_code`, or `has_tool_use` in the exported CSV. This is a **pipeline gap** relative to the ML dataset.

# 6. Dataset Cleaning

**Implementation:** `data_cleaning.clean_prompts_dataframe()` in `src/github_repo_miner/data_cleaning.py`

**Called from:** `prompt_analysis.run_prompt_analysis()` and (indirectly) ML loading.

## 6.1 Cleaning rules

| Rule | Function / pattern | Reason |
|------|-------------------|--------|
| Empty text | `len == 0` | No content |
| Acknowledgments | `ok`, `thanks`, `continue`, `lgtm`, etc. | Not substantive prompts |
| Too short | `< 25 chars` or `< 4 words` (CJK: alternate thresholds) | Low information |
| Too long | `> 8000 chars` | Outliers / log dumps |
| CI runner logs | `goreleaser-action@`, `/home/runner/work/` | Pasted CI output |
| Browser console | `react-dom_client.js`, `Fast Refresh` | Pasted devtools noise |
| IDE diagnostics | JSON diagnostic arrays | Not prompts |
| Slash commands | `/command` | IDE control, not dev intent |
| Local command XML | `<command-name>`, etc. | Cursor internal messages |
| Path-only prompts | File path with < 12 chars of other text | Accidental path paste |
| Stack traces | 5+ `at fn (file:line)` lines | Error dumps |
| Duplicates | Exact `prompt_text` match | Redundant rows |

# 7. Feature Engineering

Features are created in two places:

1. **`prompt_analysis.py`** — linguistics, regex intents, clustering
2. **`ml_research/data.py`** — `prompt_type`, session/repo aggregates for ML

## 7.1 Text and prompt features

| Feature | Meaning | Implementation | Why it matters |
|---------|---------|----------------|----------------|
| `char_len` / `word_len` | Prompt size | `str.len()`, `str.split()` | Longer prompts may correlate with complex tasks |
| `line_count` | Multiline structure | Count `\n` | Spec vs one-liner |
| `has_question` | Contains `?` | regex | Question vs imperative style |
| `has_code_mention` | Mentions ``` or file extensions | regex | Technical vs general prompt |
| `starts_imperative` | Starts with "add", "fix", etc. | regex anchor | Command-style prompting |
| `turn_index` | Position in session | From parser enumeration | Later turns may be follow-ups |
| `prompt_type` | Rhetorical style (question, imperative, debug, …) | `derive_prompt_type()` in `ml_research/data.py` | Weak style taxonomy |

## 7.2 Response and outcome features (labels / analysis only)

| Feature | Meaning | Implementation |
|---------|---------|----------------|
| `agent_response_length` | Agent reply size | `len(agent_response)` |
| `generated_code_length` | Total fenced code chars | Sum of code blocks |
| `code_block_count` | Number of ``` blocks | Fence regex count |
| `code_languages` | Languages in fences | Parsed fence tags |
| `code_to_text_ratio` | Code / response length | Ratio |
| `session_turn_count` | Conversation length | `max(turn_index)+1` per `source_file` |

**Critical:** These are **not used as ML inputs** for behavior prediction (would be leakage). They are **targets** or descriptive stats.

## 7.3 Tool-related features

| Feature | Meaning | Implementation |
|---------|---------|----------------|
| `has_tool_use` | Agent used tools | `<tool-use>` in assistant turn |
| `has_generated_code` | Agent produced code | `code_block_count > 0` |

There is no `tool_call_count` column; tool use is **binary** per turn.

## 7.4 Repository metadata features (ML inputs for Task 2)

Computed in `ml_research/data.py`:

| Feature | Meaning |
|---------|---------|
| `repo_prompt_count` | Prompts from this repo in corpus |
| `repo_median_words` | Typical prompt length in repo |
| `repo_code_rate` | Fraction of repo prompts with code |
| `repo_tool_rate` | Fraction with tool use |
| `repo_stars_log` | `log1p(stars)` if available |

## 7.5 Embedding and clustering features

| Feature | Method | File |
|---------|--------|------|
| SBERT embedding | `all-MiniLM-L6-v2` (384-d) | `representations.encode_sbert()` |
| TF-IDF | 2000 features, 1–2 grams | `representations.build_tfidf()` |
| `cluster` | K-means, k chosen by silhouette | `prompt_analysis.run_prompt_analysis()` |
| `umap_x`, `umap_y` | 2D UMAP projection | Same |

**Cached embeddings:** `outputs/ml/prompt_embeddings.npy` (shape: 3673 × 384)

# 8. Label Creation and Classification Problem

## 8.1 Primary labels for agent behavior (Task 2 — core)

| Label | Type | Assignment rule |
|-------|------|-----------------|
| **`has_generated_code`** | Binary | `True` if assistant turn contains ≥1 fenced code block |
| **`has_tool_use`** | Binary | `True` if assistant turn contains `<tool-use>...</tool-use>` |

**Why these two:**

- Directly observable from SpecStory logs (no human annotation)
- Map to actionable agent modes: **code emission** vs **tool invocation**
- Align with the research question about predicting agent next actions

### ML formulation (Task 2)

```
INPUT:  SBERT(prompt_text) ⊕ metadata ⊕ repo_features
           ↓
MODEL:  Logistic Regression | Random Forest | XGBoost
           ↓
OUTPUT: P(has_generated_code=1)  or  P(has_tool_use=1)
```

**Inputs explicitly excluded:** `agent_response`, `generated_code`, `has_*` labels themselves.

## 8.2 Weak intent labels (Task 1 — auxiliary)

`primary_intent` is assigned by regex rules in `prompt_analysis._add_intents()`:

```python
INTENT_RULES = {
    "debug_fix": r"\b(fix|bug|error|...)\b",
    "implement": r"\b(add|create|implement|...)\b",
    # ... 10 categories total
}
primary_intent = first matching rule, or "unclassified"
```

**Current distribution:**

| `primary_intent` | Count | % |
|------------------|-------|---|
| unclassified | 2,244 | 61.1% |
| implement | 508 | 13.8% |
| debug_fix | 460 | 12.5% |
| *(8 other classes)* | 461 | 12.6% |

## 8.3 Limitations of current labeling

| Limitation | Impact |
|------------|--------|
| Only two **behavior** classes | Cannot distinguish explain vs debug vs refactor outcomes |
| Intent labels are regex-derived | Task 1 metrics are inflated for lexical models |
| 61% unclassified | Intent taxonomy is incomplete |
| Binary tool flag | No tool-type breakdown (read file vs shell vs search) |
| Single-turn pairing | No multi-turn context window in features |

## 8.4 Future label expansion (not implemented)

- explain_code, debug_code, clarify, search_docs, run_tests, edit_files, refactor, plan_architecture

# 9. Machine Learning Pipeline

**Entry:** `python run_ml_research.py`  
**Orchestrator:** `src/github_repo_miner/ml_research/pipeline.py` → `run_ml_research()`

## 9.1 Phase 1 — Dataset analysis

- Load `specstory_prompts_clustered.csv`
- Recompute derived columns
- Write `outputs/ml/tables/dataset_summary.json`, label distributions, leakage notes

## 9.2 Phase 2 — Representations

| Representation | Description |
|----------------|-------------|
| `sbert` | 384-d MiniLM embedding |

# 11. Scientific Interpretation of Results

## 11.1 What was learned about LLM coding behavior?

1. **Code generation is predictable (AUC 0.88).** Before the agent responds, prompt text + repository context carries substantial signal about whether the reply will contain fenced code. This supports the core research hypothesis.

2. **Repository context matters.** `repo_code_rate` and related features improve prediction — some repos are systematically more code-oriented than others, independent of any single prompt.

3. **Lexical features match lexical labels.** TF-IDF dominates intent classification because `primary_intent` is regex-defined. SBERT embeddings do **not** outperform TF-IDF on this weak label — an important methodology lesson.

4. **Tool use is harder.** Despite high ROC-AUC, low recall means practical utility is limited without addressing class imbalance or richer labels.

5. **Response size is not predictable from prompts alone.** R² ≈ 0 for response/code length suggests those outcomes depend on agent policy, context window content, and task difficulty — not just prompt wording.

## 11.2 Patterns before different agent actions

| Agent action | Prompt patterns associated (informal) |
|--------------|---------------------------------------|
| **Generate code** | Implementation language, repo with high code rate, longer technical prompts |
| **No code** | Questions, acknowledgments (if not filtered), explanatory prompts |
| **Tool use** | Rare; weakly associated; model defaults to negative class |

## 11.3 Can agent behavior realistically be predicted?

**Partially yes** for binary code generation — with caveats:

- Evaluation is on **held-out repositories**, not random rows (stronger test)
- Labels are turn-level, not session-level
- No multi-turn context encoded (only `turn_index` as a number)
- 65 repos may not generalize to all developer populations

## 11.4 Real-world applications

| Application | How results could be used |
|-------------|---------------------------|
| **Agent routing** | If P(code) is high, allocate code-specialized model |
| **UX hints** | Warn user their prompt style tends not to produce code |
| **Efficiency** | Pre-load tools when P(tool_use) is high (needs better recall) |
| **Monitoring** | Flag anomalous prompt→outcome patterns per repo |

# 12. Limitations and Future Work

## 12.1 Dataset limitations

| Limitation | Detail |
|------------|--------|
| SpecStory availability | Only repos that commit SpecStory logs; biased toward Cursor users who opt in |
| Repository concentration | Top 10 repos = 52% of prompts |
| Small repo count | 65 repos in canonical set |
| Selection bias | Public GitHub repos ≠ all development |
| Cleaning attrition | 37K → 3.7K rows; may remove valid short prompts |
| CLI vs notebook gap | Full turn-pair extraction not in CLI path |

## 12.2 Model limitations

| Limitation | Detail |
|------------|--------|
| No transformer fine-tuning | Frozen SBERT only |
| No sequence modeling | Each turn independent; no conversation history embedding |
| Binary tool label | No multi-class agent actions |
| Weak intent labels | 61% unclassified |
| No statistical tests | No CIs, p-values, or cross-validation |
| Repo features computed on full corpus | Minor leakage for repo aggregates |

## 12.3 Future improvements

1. **Unify extraction** — wire `parse_specstory_turns()` into CLI `prompt_extraction.py`
2. **Human-annotate** 300–500 prompts for gold intent labels
3. **Multi-class agent actions** — explain, edit, test, search, plan
4. **Conversation context** — embed prior N turns, not just current prompt
5. **Transformer fine-tuning** — LoRA on small encoder for behavior prediction
6. **GroupKFold CV** — confidence intervals on metrics
7. **Larger corpus** — expand beyond 65 repos
8. **Remove duplicate/stale outputs** — legacy blob folders
